# Contrat — Modèle en étoile et chargement de l'entrepôt

**Projet :** DataFlow360
**Sprint :** Sprint 3
**Fonctionnalité :** F1.10 — Modèle en étoile et chargement de l'entrepôt
**Responsable :** Aissata DIALLO · **Relecteur :** Seydina WADE
**Schéma PostgreSQL :** `dwh` (réservé depuis le Sprint 0, voir `docs/contrats/zones_stockage.md` §4)
**Module :** `src/integration/chargement.py`, `src/integration/verifier.py`

Ce document fixe les tables, les grains, les clés et les règles de
chargement de l'entrepôt. Il doit être lu avant d'écrire la moindre
vue d'indicateur, le tableau de bord, ou une vérification.

## 1. Les tables

| Table | Rôle | Grain |
|---|---|---|
| `dwh.fait_ligne_commande` | les ventes : prix, frais de port, quantité | une ligne d'article |
| `dwh.fait_commande` | le cycle : statut, dates, délai, montant payé, nombre de paiements | une commande |
| `dwh.dim_date` | le calendrier : jour, semaine, mois, année | un jour |
| `dwh.dim_client` | la personne, avec sa localisation | une personne (`customer_unique_id`) |
| `dwh.dim_produit` | le produit vendu, sa catégorie, la fiche rattachée, la langue | un produit vendu |
| `dwh.dim_vendeur` | le vendeur | un vendeur |

Conforme au vocabulaire déjà fixé par `zones_stockage.md` : préfixe
`fait_`/`dim_`, clé de substitution entière par dimension, distincte
de l'identifiant métier conservé comme attribut.

## 2. Les clés de substitution

Chaque dimension porte une clé entière générée
(`GENERATED BY DEFAULT AS IDENTITY`), indépendante de l'identifiant
métier. Le choix `BY DEFAULT` plutôt que `ALWAYS` est volontaire : il
permet d'insérer explicitement la ligne `0` de chaque dimension (§4)
sans syntaxe particulière.

Avec l'historisation complète (§5), l'identifiant métier n'est **plus
unique à lui seul** dans une dimension : une personne, un produit ou
un vendeur peut avoir plusieurs lignes au fil du temps, une par
version. Chaque dimension porte donc un **index unique partiel**,
sur l'identifiant métier, restreint aux lignes courantes :

```sql
CREATE UNIQUE INDEX ON dwh.dim_client (customer_unique_id) WHERE est_courante;
```

C'est cet index qui garantit qu'il n'existe jamais deux versions
courantes à la fois pour la même personne.

Les tables de faits portent leur grain comme clé naturelle
(`order_id` pour `fait_commande`, `(order_id, order_item_id)` pour
`fait_ligne_commande`) : une ligne de fait n'a pas besoin d'une ligne
« inconnue », elle existe ou n'existe pas.

## 3. Détail des tables

### `dwh.dim_date`

| Colonne | Type | Contenu |
|---|---|---|
| `date_id` | INTEGER PK | `AAAAMMJJ`, ex. `20170315` — lisible, trié naturellement |
| `date` | DATE NOT NULL UNIQUE | |
| `annee`, `trimestre`, `mois`, `semaine_iso`, `jour` | INTEGER | |
| `nom_jour`, `nom_mois` | TEXT | en français |

`dim_date` n'est **pas historisée** (pas de `valide_du`/`valide_au`) :
un jour calendaire ne change jamais de définition — le 15 mars 2017
reste le 15 mars 2017. L'historisation (§5) ne s'applique qu'aux
dimensions qui décrivent une entité métier dont un attribut peut
changer : client, produit, vendeur.

⚠️ **Pas de colonne `jour_ferie` dans cette migration.** Elle dépend
du service référentiel (Ndeye Penda, section 5 de la répartition),
livré en parallèle. Une migration ultérieure l'ajoutera — voir §7.

Les trois dimensions suivantes (`dim_client`, `dim_produit`,
`dim_vendeur`) sont **historisées** : chacune porte, en plus de ses
attributs métier, les trois colonnes de validité définies au §5 :

| Colonne | Type | Contenu |
|---|---|---|
| `valide_du` | DATE NOT NULL | date à partir de laquelle cette version est connue |
| `valide_au` | DATE, nullable | date de fin de validité ; `NULL` tant que la version est courante |
| `est_courante` | BOOLEAN NOT NULL | `CHECK (est_courante = (valide_au IS NULL))` |

## 4. La ligne « inconnu » de chaque dimension

Chaque dimension reçoit, à la création de la table, une ligne d'identifiant `0` :

| Table | Valeurs de la ligne `0` |
|---|---|
| `dim_date` | `date = '1900-01-01'`, autres colonnes à `0` / `'inconnu'` |
| `dim_client` | `customer_unique_id = 'inconnu'` |
| `dim_produit` | `id_produit_olist = 'inconnu'`, `rattache = faux` |
| `dim_vendeur` | `id_vendeur_olist = 'inconnu'` |

Pour les trois dimensions historisées, la ligne `0` est **permanente** :
`valide_du = '1900-01-01'`, `valide_au = NULL`, `est_courante = vrai`,
pour toujours — elle ne ferme jamais, ce n'est pas une vraie entité
métier qui pourrait changer.

Un fait dont la référence manquerait utiliserait cette ligne plutôt
que d'être perdu. En pratique, les sources actuelles (Olist) ne
produisent aucune référence manquante sur client, produit ou
vendeur : cette ligne est une garantie défensive, pas un cas attendu
aujourd'hui.

## 5. Historisation des dimensions — SCD de type 2

`zones_stockage.md` demande que les dimensions « évoluent sans perdre
les versions passées », contrairement à la zone intermédiaire qui
s'écrase. Les trois dimensions qui décrivent une entité métier —
`dim_client`, `dim_produit`, `dim_vendeur` — suivent donc un véritable
**historique de type 2** : quand un attribut suivi change, l'ancienne
version se ferme, une nouvelle s'ouvre, l'ancienne reste consultable.

### Principe

Chaque ligne porte une fenêtre de validité :

- `valide_du` : date à partir de laquelle cette version décrit
  l'entité ;
- `valide_au` : date de fin, `NULL` tant que c'est la version
  actuelle ;
- `est_courante` : vrai si et seulement si `valide_au IS NULL`
  (contrainte `CHECK`, pour qu'aucune requête ne puisse désynchroniser
  les deux).

### Algorithme de chargement, par dimension

Pour chaque identifiant métier lu dans `staging` (ou la table de
correspondance) :

1. **Identifiant jamais vu** → une nouvelle version est insérée,
   `valide_du = date du chargement`, `valide_au = NULL`,
   `est_courante = vrai`.
2. **Identifiant déjà connu, attributs suivis identiques** à la
   version courante → **rien ne se passe**. C'est ce qui garantit
   qu'un rechargement sans changement de source est strictement sans
   effet (critère de réussite du sprint).
3. **Identifiant déjà connu, au moins un attribut suivi différent** →
   la version courante se ferme (`valide_au = date du chargement`,
   `est_courante = faux`), une nouvelle version s'ouvre
   (`valide_du = date du chargement`, `valide_au = NULL`,
   `est_courante = vrai`).

La comparaison se fait sur les attributs suivis uniquement (ville/état
pour un client, par exemple) — jamais sur la clé de substitution ni
sur les colonnes de validité elles-mêmes.

```sql
-- Principe (dim_client) ; chargement.py l'exécute par lots, pas ligne à ligne.
UPDATE dwh.dim_client AS d
SET valide_au = %(aujourdhui)s, est_courante = faux
FROM entrants AS e
WHERE d.customer_unique_id = e.customer_unique_id
  AND d.est_courante
  AND (d.ville, d.etat, d.code_postal_prefixe)
      IS DISTINCT FROM (e.ville, e.etat, e.code_postal_prefixe);

INSERT INTO dwh.dim_client (customer_unique_id, ville, etat, code_postal_prefixe, valide_du, valide_au, est_courante)
SELECT e.customer_unique_id, e.ville, e.etat, e.code_postal_prefixe, %(aujourdhui)s, NULL, vrai
FROM entrants AS e
WHERE NOT EXISTS (
    SELECT 1 FROM dwh.dim_client d
    WHERE d.customer_unique_id = e.customer_unique_id AND d.est_courante
);
```

### Simplification assumée : les faits pointent vers la version courante au moment du chargement

Un fait (`fait_commande`, `fait_ligne_commande`) référence la version
**courante** de chaque dimension au moment où il est chargé — pas la
version qui était valide à la date réelle de la commande. Sur le jeu
Olist/Rakuten, figé et chargé en un seul bloc historique, les deux
coïncident forcément : aucune commande de 2017 ne peut faire référence
à une adresse qui n'existera qu'après son premier chargement. Cette
distinction ne prendrait son sens que si la plateforme recevait des
commandes au fil de l'eau sur une longue période, avec de vrais
changements de dimension entre-temps — hors périmètre de ce sprint,
à noter pour le Sprint 4 si le flux d'événements alimentait un jour
l'entrepôt directement.

### Pourquoi `dim_date` n'est pas concernée

Voir §3 : un jour calendaire n'a pas d'attribut qui évolue, donc rien
à historiser.

## 6. Le chargement

`src/integration/chargement.py` lit la zone intermédiaire (`staging`)
et la table de correspondance (F1.9) — **jamais la zone brute**.

Ordre de chargement, dans une seule transaction (`BEGIN ... COMMIT`,
`ROLLBACK` au moindre échec) :

1. `dim_date` — généré par calcul (pas de table source), de la date la
   plus ancienne à la plus récente de `staging.olist_orders`.
2. `dim_client`, `dim_produit`, `dim_vendeur` — par la fusion SCD2 du
   §5 (fermer les versions modifiées, ouvrir les nouvelles, ne rien
   faire sur les identiques), depuis `staging.*` et la table de
   correspondance.
3. `fait_commande` — paiements agrégés par `order_id` **avant** toute
   jointure. Les clés étrangères pointent vers la ligne **courante**
   de chaque dimension au moment du chargement (`est_courante = vrai`).
4. `fait_ligne_commande` — toutes les lignes de `staging.olist_order_items`,
   y compris quand la commande parente n'a pas de ligne au sens métier
   (ce cas n'existe pas : une ligne de `order_items` est par
   définition une ligne d'article).

Les tables de faits, elles, restent au comportement de la zone
intermédiaire pour ce chargement : **vidées puis rechargées**
entièrement à chaque exécution (`TRUNCATE` puis réinsertion), pas de
fusion ligne à ligne. Ce n'est pas une contradiction avec
l'historisation : un fait n'a qu'une seule version possible — la
commande du 15 mars 2017 ne change pas de prix après coup — c'est la
raison même pour laquelle les faits n'ont pas de ligne « inconnu »
(§2) ni de colonnes de validité. Seules les dimensions, dont un
attribut peut changer sans que le fait change, ont besoin de la
fusion SCD2.

```bash
docker compose exec app python -m integration.chargement
docker compose exec app python -m integration.verifier
```

## 7. Vérifications après chargement (niveau 3)

`src/integration/verifier.py`, code de sortie `1` si l'un de ces
contrôles échoue :

- comptage `fait_ligne_commande` = comptage `staging.olist_order_items` ;
- comptage `fait_commande` = comptage `staging.olist_orders` ;
- aucun fait orphelin (toute clé étrangère pointe vers une ligne
  existante, `0` compris) ;
- somme des prix de `fait_ligne_commande` = somme des prix de
  `staging.olist_order_items` ;
- `dim_client` compte 96 096 personnes + la ligne `0`, **en ne comptant
  que les lignes courantes** (`est_courante = vrai`) ;
- pour chaque dimension historisée, au plus une ligne courante par
  identifiant métier (l'index unique partiel du §2 le garantit déjà
  en base ; la vérification le recontrôle explicitement, au cas où).

## 8. Ce qui n'est pas dans ce chargement

Aucun indicateur (vues du Livrable 3). Aucune donnée d'avis (Sprint
5). Aucun chargement MongoDB/Elasticsearch (Sprint 4). La colonne
`jour_ferie` de `dim_date`, ajoutée par une migration séparée dès que
le service référentiel est prêt.

## 9. Migration

`sql/007_entrepot.sql` — une seule migration : la création du schéma
en étoile est un seul souci au sens de `zones_stockage.md` (« ajouter
les tables d'une source/d'un schéma »), les sept tables étant
interdépendantes dès la création (clés étrangères).
